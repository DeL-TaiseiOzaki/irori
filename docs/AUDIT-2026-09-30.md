# Correctness and performance audit — 2026-09-30

Reviewed the current application at `b91a1dd` (0.1.60), with independent audits
of the renderer/editor, file/search/knowledge services, and agent/terminal/Git/
cloud services. The implementation is a scoped correction of confirmed issues,
not an architecture migration.

## Corrections

1. **Search and graph recovery.** A failed file read was stored as an unreadable index row.
   Matching size and modification time then reused the failed observation on every
   later search, including after restarting the service. Retry unreadable rows;
   keep the existing fast path for successfully indexed files and file-size guards.
   Retry factless graph-cache entries for the same reason.
2. **Live requests during a conversation read.** `useBrainAi` could replace a
   newly streamed permission or question with an older IPC snapshot, or restore
   an already answered request. Check the request/run-state revision before
   applying the snapshot and read again when it changed during the request.
   Ordinary text/tool streaming does not trigger another full-history read.
3. **Unrelated file notifications.** A change in another hibachi unnecessarily
   read the currently open document. Reconcile the document only for notifications
   from its own scope; retain workspace/explorer refreshes.
4. **Conversation memory.** Reading a conversation held its complete event
   history and full tool details until constructing the bounded view. Retain only
   the last 1,000 events while reading, shorten details to the existing view limit
   immediately, and keep the earlier-event and damaged-line accounting. Stored
   history, tool detail limits and streamed-text joining remain intact.
5. **Case-insensitive move references.** The move scan recognized differently
   cased links on case-insensitive disks, while the count and rewrite compared
   exact spellings. Carry the observed filesystem case behavior through the
   preview and rewrite, observing it at the destination after the source moves.
   Body links and supported frontmatter references follow the same rule.

## Measured effect

Five paired isolated Node 24.21.0 processes opened a synthetic history of 400
tool events with 256 KiB details each (about 100 MiB on disk), plus its two
initial events. Both versions returned the same 402 events and 6,400,000
characters of tool details. The baseline module came from `b91a1dd`.

| Reading the history | Baseline median (range) | Corrected median (range) |
| --- | --- | --- |
| Heap increase | 148 MiB (111–148) | 21 MiB (21–21) |
| RSS increase | 201 MiB (190–202) | 48 MiB (48–49) |
| Elapsed time | 270 ms (249–340) | 299 ms (258–423) |

This is a memory improvement, not a measured history speedup. Reading still
parses the entire JSONL, and shortening tool details must copy their prefix to
release the original string. The regression also opens this workload in a
separate process limited to a 64 MiB heap: the old reader runs out of memory,
the corrected reader succeeds. The ignored reproduction is
`test-results/services-conversation-benchmark.py`; the bounded-heap test is in
`tests/conversations.test.ts`.

The unrelated-notification regression counts actual document-read requests:
one notification from another hibachi now causes zero reads of the open
document instead of one. A notification from its own hibachi still causes one.

## Remaining limits

- Reading a conversation still scans its JSONL from the beginning to preserve
  damage accounting and streamed-event joining. Indexed pagination is a separate
  change, as is bounding a single very large merged text response.
- Conversation snapshots have no stream cursor. The control-state races are
  covered here; exact reconciliation of ordinary text fragments with a snapshot
  taken during streaming is a separate protocol change.
- Search still walks and stats eligible files to validate its cache. Replacing
  that with watcher-only invalidation needs evidence about missed events and
  disconnected roots; a persistent cache alone cannot provide that guarantee.
  Unreadable cache rows do not distinguish temporary I/O failures from invalid
  UTF-8/NUL-containing text, so those invalid files below the size limit are
  retried as well. Oversized files remain stat-only skips.
- `KnowledgeStore.history()` reads all run records and their outcomes before
  showing the newest 100, with outcome reads performed sequentially. Selecting
  the displayed records first and overlapping those reads is a further
  performance candidate; it was not benchmarked or changed in this correction.
- These checks use disposable local data and CLI protocol fixtures. They do not
  establish performance on a mounted Drive or an installed Windows/macOS app,
  nor real provider acceptance.
- No whole-application speedup is claimed. Any measured conversation improvement
  applies to the documented synthetic history workload.
