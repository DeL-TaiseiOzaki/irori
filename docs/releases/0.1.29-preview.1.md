# irori 0.1.29 — Update irori from inside the app with one button

From this version, an installed irori updates itself. When a newer version is
published, press **更新して再起動**: irori downloads it, checks it and reopens as
the new version, without visiting the website or running an installer. An
installed 0.1.28 or earlier is offered this by **更新を確認**, but it cannot
update itself yet: install 0.1.29 once from the download website, as below.
Updates after that need only the button.

## What changed

**irori notices new versions by itself.** An installed irori checks the public
releases 10 seconds after it starts and then every hour. When something newer
exists, the startup screen and the workspace sidebar show it with the installed
and published versions. Nothing appears when there is nothing new, and
**更新を確認** still checks on demand.

**One button updates and restarts.** **更新して再起動** downloads the new
version with a progress bar and a **キャンセル** button, checks that the file is
exactly the one the release lists in `SHA256SUMS.txt`, prepares it and restarts
irori. The restart works like closing the window: drafts are saved first, a
running agent or terminal asks before it is stopped, and a Git operation in
progress has to finish. If you choose to stay, **再起動して更新** waits for you
without downloading again.

**If irori cannot update itself, it says why.** A copy that was not installed by
the Windows installer, a Mac app still inside the disk image or the Downloads
folder, a folder irori cannot write, or a failed download keeps
**インストーラーを取得** and **変更点を見る**, which open the release in the
browser as before.

**On Windows**, the installer that set irori up applies the update beside the
running version, so a failed update leaves the current version working. Each
release now also carries `irori-<version>-full.nupkg`, the file this uses.

**On the Mac**, irori copies the new version out of the published disk image,
verifies its signature, identifier and version, and swaps it into place when it
restarts. Because irori downloads the file itself, macOS does not ask you to
approve the new version again. If macOS refuses to let irori replace itself, the
notice says so and points to **システム設定 → プライバシーとセキュリティ →
アプリ管理**, and the installed version stays as it was.

Details: [in-app updates](https://github.com/DeL-TaiseiOzaki/irori/blob/main/docs/UPDATES.md),
[ADR 010](https://github.com/DeL-TaiseiOzaki/irori/blob/main/docs/decisions/010-in-app-updates.md).

## Installing

**Windows 11 x64:** download `irori-0.1.29-windows-x64-Setup.exe` and run it. The
installer carries no distribution signature, so Windows shows a warning that the
publisher cannot be verified.

**Mac (Apple silicon):** download `irori-0.1.29-macos-arm64.dmg`, open it, and
drag **irori** into **アプリケーション**. Intel Macs are not supported. The first
launch is refused because the package carries no distribution signature. Open
**システム設定 → プライバシーとセキュリティ**, find irori's blocked notice under
セキュリティ, and press **このまま開く**. The button appears only just after an
attempt to open the app, so if it is missing, open irori again and return to
that pane. Later launches behave normally. Keep irori in **アプリケーション**:
the in-app update replaces the app where it is.

## Verification

The published files are the artifacts of the CI run for the commit named under
**Exact package** below, unchanged except for their download names. Each package
job launches the packaged application from a different path and exercises SDK
imports, save/undo/redo, native clipboard image paste, the CSV graph, Japanese
note and terminal file saves, private drafts, recoverable note deletion after
restart, single-instance ownership, one search and bundled rclone. On macOS 26 it
first verifies the bundle and the copy inside the disk image. Tests use
disposable data and do not run a real model turn.

For this change, the Windows package job installs the Setup.exe on the runner,
applies the build's own `-full.nupkg` through Squirrel's `Update.exe`, and sees
the new version start after its parent exits. The Mac package job stages the
disk image into a temporary Applications folder with the real `hdiutil`,
`ditto`, `codesign` and `plutil`, swaps the bundles, and sees Launch Services
open the new one. Behavior tests cover checksum, size, redirect and HTTPS
refusals, cancellation, stalled downloads, failed preparation, each rollback and
the relaunch script; the new Electron UI suite covers the notice's states.

## Remaining boundaries

Passing CI is not acceptance on an installed device. The first real in-app
update is from 0.1.29 to the next version, on Windows 11 and on macOS 26, where
macOS's App Management protection has yet to be observed. An update is trusted
as the website download is, through HTTPS to GitHub and the release's
`SHA256SUMS.txt`; neither carries a distribution signature. Installation,
Japanese input, real CLI accounts, Git operations and Google connections still
need device trials. Writing to Google Drive and running VS Code extensions remain
separate work.
