# irori 0.1.5 — Apple silicon Mac preview

This delivery adds the first Mac download. The application behaviour is the same
0.1.5 that Windows already runs. What changed is that the Mac package is signed,
so a downloaded copy can be opened at all, and the manual update check now knows
which installer belongs to a Mac. A reader already running 0.1.5 on Windows does
not need to reinstall: the EXE here is a rebuild of the same application source,
not a new version.

## Installing on a Mac

Download `irori-0.1.5-macos-arm64.dmg`, open it, and drag **irori** into
**アプリケーション**. This build is for Apple silicon (M series); Intel Macs are
not published.

The first launch is refused, because the package carries no distribution
signature. Open **システム設定 → プライバシーとセキュリティ**, find irori's blocked
notice under セキュリティ, and press **このまま開く**. Later launches behave
normally. The exact wording depends on the macOS version, so please report what
is displayed.

## Why a Mac download existed only now

Forge copied Electron's own binaries into the Mac bundle and sealed nothing, so
every earlier Mac package shipped with zero `_CodeSignature` entries and Mach-O
members that still identified themselves as `Electron`. CI could launch such a
build, because a locally written file carries no quarantine attribute. A browser
download does, and Gatekeeper reports an unsealed bundle as a damaged
application, with no route for the reader to continue. Publishing that file
would have handed the owner an unopenable download.

The bundle is now ad-hoc signed while packaging. That needs no Apple account,
and it changes Gatekeeper's answer from a damaged application to an unverified
developer, which System Settings can override. The signed build runs under the
hardened runtime with Electron's own entitlements, which notarization will also
require. It is still not a distribution signature: no identity stands behind it
and it carries no notarization ticket, which is why the approval step above is
required. Developer ID signing and notarization remain separate work.

The Mac package job verifies the bundle Forge produced before launching it: the
`_CodeSignature` seal exists, `codesign --verify --deep --strict` passes over the
app, its helpers and its frameworks, the identifier is
`io.github.deltaiseiozaki.irori`, the signature is ad-hoc and the hardened
runtime flag is set. Gatekeeper's own verdict is recorded rather than asserted,
because `spctl` rejects unnotarized code by design and the evidence should say
so; both checks report `valid on disk` and `satisfies its Designated
Requirement`, then `rejected` from `spctl`. That job then launches the signed
package from a different path and exercises SDK imports, save/undo/redo, native
clipboard image paste, the CSV graph, Japanese note and terminal file saves,
private drafts, recoverable note deletion after restart, single-instance
ownership and bundled rclone. Configured OAuth checks stop at the local browser
handoff. Tests use disposable data and do not run a real model turn.

## Remaining boundaries

Passing CI is not acceptance on an installed Mac. Installation, the approval
step above, Japanese input, real CLI accounts, GitHub operations and Google
connections still need the owner's device trial on the MacBook M5 Pro.

Google connections remain read-only. On a Mac they use macOS's own NFS mount and
need no extra installation, but no real mount has been observed on a device.
Drive uploads, real OpenCode and Pi model turns, notarized signing, Intel Mac
packaging and cross-device history remain separate work.

The manual update check now resolves `irori-<version>-macos-arm64.dmg` on Apple
silicon. Preview iterations of an already installed version are not advertised
as upgrades, so an installed 0.1.5 reports itself current.
