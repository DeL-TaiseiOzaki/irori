# irori 0.1.84 preview 1 — One definition for what agent code repeated

Nothing irori does changes in this release. Code the agent service, its
conversation records and the domain model each spelled out more than once now
has one definition:

- The hibachi categories, a run's outcomes and a hand-off's states are each one
  list that the type, the validators and the `irori` command read.
- The files at a hibachi's top that belong to Schema are one list, read both
  where a path is classified and where a layer folder name is refused.
- A new conversation's details, its owner, and the messages repeated across
  the agent service and the conversation store are each written once. The
  conversation migration uses the same definitions.
- The file a tool call names is read by one helper, and the write check reads
  only the names Claude Code's write tools use, as before.
- The `hibachi` and `irori` commands share their client's request code, and
  every loopback bridge shares its server.
- Codex's app server is started and greeted by one module, for both runs and
  the model list. CLI version checks use the same output reader as model lists.
- Smaller repeats: the 64 MiB material limit and the outcome file paths in the
  knowledge store, the skill front-matter pattern, the relative-path check of
  drafts and sources, and the lines of the handed-hibachi request.

## Verification

The type check and Prettier pass. The focused unit tests for the changed
modules pass, including conversations, migration, the `hibachi` and `irori`
commands, harnesses and the irori agent. A one-off test against a temporary
folder checked the person-lines bridge's answers and its refusal of a wrong
token. `npm run build`, `npm test` and all Electron UI suites pass. The tests
that need real OpenCode or Pi were skipped, and real-CLI acceptance was not
run.
