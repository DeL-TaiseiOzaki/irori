# irori 0.1.46 — Cloning private GitHub repositories with your gh sign-in

**リポジトリ・KBフォルダを登録 → GitHub から取得** (Clone from GitHub) could
refuse a private repository even though you had signed in with `gh auth login`.
irori runs your own `git`, and Git only uses the GitHub CLI's sign-in after
`gh auth setup-git`, which `gh auth login` does not always do. irori now uses
that sign-in without you having to run anything else.

## GitHub sign-in

- When GitHub refuses a clone, fetch, pull or push over HTTPS, irori tries the
  operation once more with the GitHub CLI (`gh`) providing the credentials. The
  retry takes effect only if `gh` is installed and signed in.
- The retry changes nothing in your Git configuration. It applies to that one
  operation and to `https://github.com` only. It also takes precedence over a
  stale GitHub password that a keychain may still be offering. irori never sees
  the token: `gh` hands it to Git directly.
- Your existing credential helper and SSH setup are still tried first, so a
  setup that already works behaves as before.
- When it still fails, the message says what to do next:
  - `gh` is not installed: install it and run `gh auth login`, or set up a Git
    credential helper or SSH.
  - `gh` is signed in, but its account cannot access the repository: run
    `gh auth status` to check which account that is.

## Clearer failures

- A failed Git operation shows its advice first. Under **詳細** (Details) is the
  last part of Git's own output, with passwords, tokens, credentials in URLs and
  your home folder removed.
- A failed clone no longer leaves an empty folder behind, so you can retry with
  the same folder name. If Git left any files, the folder is kept and the
  message says so.
- Error messages across irori no longer start with "Error: Error:".
- The registration dialog no longer shows an empty grey box before there is
  anything to preview.

## Installing

**Windows 11 x64:** download `irori-0.1.46-windows-x64-Setup.exe` and run it. The
installer carries no distribution signature, so Windows shows a warning that the
publisher cannot be verified.

**Mac (Apple silicon):** download `irori-0.1.46-macos-arm64.dmg`, open it, and
drag **irori** into **アプリケーション**. Intel Macs are not supported. The first
launch is refused because the package carries no distribution signature. Open
**システム設定 → プライバシーとセキュリティ**, find irori's blocked notice under
セキュリティ, and press **このまま開く**. Later launches behave normally. Keep
irori in **アプリケーション**: the in-app update replaces the app where it is.

An installed 0.1.29 or later offers this version with **更新して再起動**.

## Verification

- Unit tests (`git-github-cli.test.ts`) use a stand-in `git` and `gh` to check
  the following:
  - that a refused HTTPS GitHub operation retries once with `gh`;
  - that it does not retry for SSH, other hosts, rejected pushes or local
    operations;
  - which advice each outcome gives.
- With real Git, the same unit tests show that `gh` answers for `github.com`
  ahead of a stale helper, and that other hosts keep that helper.
- Other unit tests cover the removal of credentials and the home folder from
  Git's output, and finding `gh` on the PATH. Two more clone tests check that
  the empty folder is removed but a folder holding files is kept.
- `git-ui-smoke` now fails a clone first. It checks that the dialog shows one
  line of advice without "Error:" and that Git's output is folded under
  **詳細**. It also checks that no folder is left and that the same folder name
  then clones.
- The full build, unit tests and Electron UI suites passed.

## Remaining boundaries

- The retry covers `https://github.com` only. GitHub Enterprise hosts and SSH
  remotes use your own Git setup as before.
- Not yet tried against a private repository from an installed macOS or
  Windows 11 app. The tests use stand-ins and local repositories, never
  GitHub itself.
