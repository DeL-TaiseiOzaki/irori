# irori 0.2.79 preview 1 — A vault on an SSH host has its own agent and terminal

- The vault agent of a vault on an SSH host now takes instructions in its own
  column, as a vault of this computer does. It runs **on the host**, in the
  vault, on the CLI installed and signed in there. Until now its column showed
  only a note sending you to the irori agent.
- Its conversations are kept on the host: the history lists them, and they are
  renamed, pinned, archived, deleted, edited from a message and copied there.
  Queued instructions, sending one of them at once, stopping and the CLI's `/`
  commands work as before. A line above the conversation says which host it
  runs on.
- What its run asks (a permission, a question, configuration that runs without
  asking) is answered in irori's window, as for a hand-off.
- A file attached to an instruction is sent to the host with it.
- A run goes on if the connection is cut. irori reconnects by itself while one
  is running and shows what it missed; a run the host lost (its vault host was
  restarted) is ended in the window with a note saying so.
- The terminal of such a vault (``Ctrl+` ``, the status bar's **ターミナル** or
  the vault home's button) is now `ssh -t` to the host, in the vault's folder
  there, in your login shell on that host. It is a login of its own: what `ssh`
  asks is asked in the terminal.
- Not yet: editing such a vault from the window, the vault agent's `irori`
  command on the host, opening a path a reply from the host names, connected
  folders and routines.

## Verification

On Linux, with this machine standing in for an SSH host (another home folder,
the vault host run from source) and the protocol fixtures of Pi and Claude
Code as the CLIs there:

- `tests/remote-hosts.test.ts`: a conversation created, run, listed, read,
  renamed, copied, gone on from before a message and deleted on the host; a
  queued instruction started and a run stopped from here; a file attached here
  kept there under its id and named to the agent; a permission asked there
  answered here; a run whose vault host was killed ended in the window once the
  host answered again; the terminal's command run by `sh`, `bash` and `dash` as
  the login shell, in a folder named with quotes, `$`, a backslash and Japanese.
- `scripts/remote-hosts-ui-smoke.ts`: through the window with a stand-in `ssh`,
  an instruction sent from the vault agent's column made a file on the host,
  the history listed the conversation, and a command typed in the terminal ran
  in the vault's folder there.

Not tried: a real SSH host with a real CLI signed in there, a Windows or macOS
client (the terminal is `ssh.exe` in a ConPTY on Windows), and a login shell
other than those above (fish, zsh).
