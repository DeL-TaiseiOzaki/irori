# irori 0.2.81 preview 1 — Keep working while an agent runs

While an agent ran, irori held back far more than the run needed: any run in any
vault stopped every Git operation, adding a vault, the vault's settings, its
Schema, restoring a note and reconnecting a folder. A run keeps what it was
given when it started, so now only what would move or rewrite files a run works
on waits, and only for runs in that vault. ADR 020 D5 and ADR 042 are amended.

- **Git goes on during runs.** Staging, commits, pushes, fetches and publishing
  work while agents run. **Pull**, **履歴を統合**, resolving a conflict and
  fetching a submodule change the vault's files, so they wait for runs in that
  vault only; Pull and merge are greyed out with the reason. A routine still
  holds every Git operation, since its record of changes compares Git's status
  before and after.
- **Connections.** **再接続**, **取得**, **手元のクローンを選ぶ**,
  **フォルダを選び直す**, renaming and unregistering work during a run, and a
  folder waiting for its drive connects by itself during one. Disconnecting a
  connected folder, changing its access, **最新にする** and removing unregistered
  data still wait. The irori agent's `irori connect` works during the vault's run.
- **Vaults.** A vault can be added, created or cloned while agents run. Its
  name, look and shown layer names change during its run, in **vault の設定** and
  with `irori set`; its layer folders and its removal wait, and the sheet says so.
- **Notes, Schema and views.** **新しいノートを作成** and **今日のノート** on the
  vault's home, restoring a deleted note, editing the Schema (the irori agent's
  too, while it works), and opening the ontology and **資料と成果物** work during
  a run. Moving, renaming and deleting notes and files, and rewriting the
  indexes, still wait.
- **A GitHub connection showing フォルダ未選択 can be connected again.** When
  this device had lost a connection's folder, the link irori left at
  `contents/<name>` refused every new folder, and **取得** found that out only
  after cloning the whole repository. A link there that leads nowhere now gives
  way. One that leads to a folder is named in the message, for you to choose that
  folder or remove the link, and **取得** checks this before it clones. While a
  clone runs, the sheet says it may take minutes.

## Verification

`npm run build`, `npm test` and `npm run test:ui` pass on Linux under Xvfb, as do
the website checks.

- `scripts/harness-ui-smoke.ts`, with a fixture agent run held open, opens the
  vault menu's views, renames the vault in its settings while the folder fields
  and removal are greyed out, connects one folder and reconnects another, and
  checks that disconnecting or changing the access of the connected one is
  refused by the host and greyed out in the sheet.
- `tests/git.test.ts` commits while the vault's run holds it and checks that a
  pull is refused then.
- `scripts/your-ai-ui-smoke.ts` now expects the irori agent's Schema to be
  editable while it runs, where it expected it locked.
- `tests/repository-connections.test.ts` covers a leftover link: named before any
  clone, used when its clone is chosen, removed once it leads nowhere, and a
  folder of the person's at that place left untouched.
- `tests/local-folders.test.ts` checks that a waiting folder is linked by itself
  once nothing holds it back, and that `linked` and `isLinked` follow the link.
- `tests/irori-command.test.ts` now expects `irori connect` and `irori set` to
  work while the vault's own agent runs, and `irori remove` and `irori layer` to
  wait.

The note shown while a repository clones is not exercised by a smoke. Not tried
on macOS or Windows.
